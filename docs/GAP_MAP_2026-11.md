# PekoHub gap map — 2026-11-01

Where PekoHub stands against the MVP runtime (peko-runtime `ba64ee4c`) and desktop, and what
separates it from a production-grade public website and service.

Severity: **P0** blocks the runtime/desktop MVP from using the Hub · **P1** needed for a credible
public launch · **P2** production polish / scale.

## Decisions (2026-11-01)

1. **The Hub is a seed registry.** Not a `.peko` snapshot registry — snapshots are too large to
   store at this stage. A seed is a stripped `principal.toml` (runtime ADR-060); a snapshot stays
   a local file moved by hand.
2. **The API host is `api.pekohub.ai`.** `pekohub.ai` is the website only.
3. **The web chat UI is removed; the chat endpoint stays.** The website stops offering chat.
   The backend proxy (`POST /v1/public/pekos/:owner/:name/chat` → tunnel → runtime) stays as the
   path for clients that have no runtime of their own — a future mobile app.

The Hub's job after these decisions: **accounts · runtime registration · tunnel relay (channels,
plus chat for runtime-less clients) · principal directory · seed registry · website.**

## 2. Remove the web chat UI; keep the endpoint for runtime-less clients (P0 — decision 3)

**Remove (pekohub frontend):** `components/public-chat/*`, `hooks/usePublicChat.ts`,
`lib/sse.ts`, the chat panel on `/peko/:owner/:name`, the ToS and quota fields in the dashboard
modal (no first-party client exercises them), and the chat copy on the landing page. The profile
page becomes a profile with "Message in Peko" (see U3).

**Keep (backend, runtime, tunnel):** the public chat route, `TunnelRouter.proxyChat` /
`proxyStream`, the `proxied_request` / `stream_*` tunnel arms, bridge tokens + `/v1/jwks.json`,
the runtime's proxied-request ingress (it already funnels into a peer DM channel through
`PeerChildTurns::ensure_child_ingress`), quotas and their columns.

**Tighten what stays:**
- **Anonymous visitor chat off by default.** With no website chat, nothing first-party sends
  visitor traffic, so the cookie path is an open door for anyone with a link to spend an
  owner's model budget. Put it behind a server flag (default off) and require an account
  (`Authorization: Bearer`) otherwise. A mobile app signs in, so it doesn't need visitors.
  The visitor code (cookie, `ActorRef::Visitor` on the runtime) can stay dormant.
- **Desktop uses the runtime, not the proxy.** The desktop has a local runtime, so "add a remote
  peko" should become *add a contact* and message it over the local runtime's peer DM
  (`ChannelSend` to `principal:hub:<UUID>`, relayed by `tunnel_channel_event`). One conversation
  record, owned by the user's own runtime, the ADR-073 channel model. Retire
  `clients/hub_remote_client.rs`, `ResolvedRuntime::HubRemote`, and `storage/local_chat_log.rs`
  (desktop #108/#109) once that works. The proxy is then reserved for runtime-less clients.
- **Mark it as not finished for mobile.** The endpoint is one SSE stream per message with no
  Hub-side conversation: a reply produced after the stream closes (a parked run, ADR-089) or
  while the phone is backgrounded is lost, and there's no history fetch. A mobile client will
  need a reconnectable stream (resume by cursor), a history read, and push notifications. Record
  that in the endpoint's docs so nobody mistakes it for done.

## 3. Contract gaps with runtime + desktop (P0)

| # | Gap | Evidence | Fix |
|---|---|---|---|
| C1 | **Desktop sign-in has no server.** The desktop runs OAuth 2.0 + PKCE against `/oauth/authorize` and `/oauth/token` (authorization_code, refresh_token) with a loopback redirect. The Hub has neither route. | desktop `src/lib/oauth.ts:54`, `src-tauri/src/commands/hub_http.rs:106`; hub `routes/auth/oauth.ts` has only `/v1/auth/:provider/authorize\|callback`, `/refresh`, `/me`, `/logout` | Build an OAuth authorization server on `api.pekohub.ai`: desktop as a public client, PKCE S256, consent page on `pekohub.ai`, loopback redirect URIs (RFC 8252), short-lived access + rotating refresh tokens (reuse ADR-001) |
| C2 | **Runtime registration needs a hand-copied API key.** `register_runtime(origin, api_key)`: the user signs in on the web, mints a `pkr_` key, and pastes it. | runtime `tunnel/registration.rs:109` | Desktop: register with its OAuth token right after sign-in. CLI: **device authorization grant** (RFC 8628) — `peko runtime register` shows a code, the user approves on `pekohub.ai`. API keys stay for automation |
| C3 | **Switch every client to `api.pekohub.ai`.** The SPA already calls it. The runtime defaults to `wss://pekohub.ai/v1/tunnel` (rewriting `pekohub.org` → `pekohub.ai`) and derives REST from it; the desktop's `DEFAULT_HUB_URL` is `https://pekohub.ai`. | runtime `tunnel/credential.rs:166`, `tunnel/registration.rs:274`, `tunnel/hub_directory.rs:586`; desktop `src/lib/api.ts:1103` | Runtime: default tunnel `wss://api.pekohub.ai/v1/tunnel`; migrate saved `pekohub.org`/`pekohub.ai` registrations to `api.`. Desktop: default API base `https://api.pekohub.ai`. Rewrite `DEPLOYMENT.md` (it still describes the retired dual-hostname split) |
| C4 | **Two origins mean two URLs per concept.** Share links and seed pages live on the web origin (`pekohub.ai/peko/<owner>/<name>`, `pekohub.ai/seeds/...`); the API lives on `api.`. The desktop's `peko_share_link` builds the link from the hub it's registered with, so after C3 it would emit `api.pekohub.ai/peko/...`. `AddRemotePrincipalModal` parses `pekohub.ai/peko/...` links. | desktop `hub_http.rs:130`, `AddRemotePrincipalModal.tsx:139` | Hub publishes its web origin (e.g. `GET /v1/meta` → `{ webOrigin }`, or `shareUrl` on directory hits); clients build links from that and map web links → API lookups. The API serves CORS for `pekohub.ai` with credentials; the website's session cookie is scoped accordingly |
| C5 | `GET /v1/runtimes/:id/status` is called by the desktop and doesn't exist. | desktop `useRuntimes.ts` | Add it, or drop the desktop call in favour of `/v1/runtimes` |
| C6 | **Shared wire types are hand-synced** across runtime Rust (`tunnel/protocol.rs`), hub TS (`tunnel-protocol.ts`), and `packages/shared`. C1 and C5 slipped through this way. | — | Generate from one schema (JSON Schema/OpenAPI) and add a cross-repo contract test running the real runtime tunnel client and desktop OAuth flow against the hub in CI |

## 4. Seed registry (P0/P1 — decision 1)

The runtime side is already decided (runtime ADR-060, ADR-066 D7): a seed is `<name>.seed.toml`,
downloaded and grown with `peko create -s <file>`; the runtime has no registry client and no push.
The Hub can serve and display seeds. **Nothing can publish one.**

| # | Gap | Fix |
|---|---|---|
| S1 | **No publish path.** The only write path is OCI `PUT /v2/.../manifests` + blob upload, which had exactly one producer — the runtime registry client deleted in ADR-066 D7. | Add a seed publish API on `api.pekohub.ai` (`POST /v1/seeds` with the TOML body; new version = new upload) used by the website (drag-and-drop / paste), the desktop, and the CLI with the OAuth token. Keep OCI storage underneath only if it earns its keep; a seed is a few KB, and a `seed_versions` table with the TOML in Postgres (or R2) is simpler. **Recommend:** retire the public `/v2` OCI surface and its blob GC, and keep content digests for integrity |
| S2 | **No way to make a seed from an existing peko.** The runtime has no export that strips identity, owner, contacts, Hub IDs, keys, and runtime-local state from a `principal.toml`. | Runtime: `peko seed <name> [-o file]` (+ desktop "Share as seed"). Hub: validate on publish against the same rules (reject owner/identity/key fields, size cap, schema version) so a hand-edited file can't leak identity |
| S3 | **No way to grow a seed from the desktop.** No create-from-seed flow (`CreatePrincipalModal` / `ImportPekoModal` handle new pekos and `.peko` snapshots only). | Desktop: "Create from seed" — from a file, and from a Hub seed page via deep link (`peko://seed/<owner>/<name>@<version>`) |
| S4 | **Seed page and catalog.** Today: catalog, detail with README, versions, a copy-paste `peko create` command. | Production page: rendered description/README, what the seed contains (roles, skills, model requirements — parsed from the TOML), version history with changelog, download count, "Open in Peko" button, publisher profile, report button |
| S5 | **Trust in seeds.** A seed is DNA, not code — but it can carry roles/prompts that steer a peko. No signatures (runtime ADR-066 D7 left trust to the operator). | Hub-side: content review queue for public seeds, report/takedown, verified publishers, a malicious-prompt scan. Optional later: publisher signatures the runtime displays at `peko create` |
| S6 | **Naming and ownership.** `namespace/name` with publisher-claims-first. | Reserved names, handle squatting policy, transfer, deprecate/yank versions (exists for OCI; port to the new model), immutable versions |

## 5. Runtime features the Hub doesn't reflect yet (P1)

| # | Runtime feature | Hub gap |
|---|---|---|
| R1 | **Offline runtimes** (ADR-072 durable delivery) | A `tunnel_channel_event` to a runtime that isn't connected has nowhere to wait. The runtime has a `channel_outbox`; the Hub needs a bounded per-runtime inbox (store-and-forward with TTL) so a DM sent while the peer is offline arrives on reconnect |
| R2 | **Ownership + one online copy** (ADR-081) | Backend done (move/transfer approvals). No web UI to approve a move, transfer a peko, or see which runtime holds it — raw `POST` endpoints only. Needs email or desktop notification of a pending approval |
| R3 | **Group channels** (ADR-049/082) | The relay forwards events and invites. No web visibility, and none needed for MVP; note that groups spanning runtimes depend on R1 for reliability |
| R4 | **Attachments** (ADR-088) | No attachment field on the tunnel (`attachments: Vec::new()`), so cross-runtime DMs drop them. Needs relay-through-R2 with presigned URLs, size/type limits, TTL |
| R5 | **Avatars** | Emoji/monogram only. Fine for MVP; production wants uploaded images (R2 + resizing) for users and pekos |

## 6. Website / UI presentation (P1 → P2)

With chat gone, the website's job is: **explain Peko, get people to install the desktop, let them
find pekos and seeds, and manage their account, runtimes, pekos, and seeds.**

| # | Gap | Notes |
|---|---|---|
| U1 | **Honest system state** | The hero hard-codes "relay online · OCI v1.1". With no API, the directory shows skeletons or a spinner, then a raw error string. Needs designed empty, error, and offline states, and a status page |
| U2 | **Information architecture** | Nav is "Pekos / Seeds". Missing: product landing with a download CTA for the desktop (the primary funnel), how it works, docs, pricing ("free during beta" is fine), changelog/blog, about, footer with legal links. Landing copy is built around browser chat and has to be rewritten |
| U3 | **Peko profile page** (`/peko/:owner/:name`, the share-link landing) | Becomes a profile, not a chat: avatar, description, owner, online state, the seed it grew from (if any), and **"Message in Peko"** (deep link into the desktop, which adds the contact via the directory; falls back to the download page). Report button |
| U4 | **Share-link previews / SEO** | Pure client-rendered SPA; `index.html` has no OpenGraph/Twitter tags, so every `/peko/...` and `/seeds/...` link previews as generic "PekoHub". Needs edge-rendered meta per page (Cloudflare Pages Functions), OG images, sitemap, robots, canonical URLs |
| U5 | **Owner console** | Today: exposure, profile fields, quotas/ToS (UI removed per §2), invites. Needed: runtimes (online, version, last seen, unregister), pekos (exposure, move/transfer — R2), seeds (publish, versions, deprecate, stats), API keys, security events |
| U6 | **Account** | GitHub/Google only. No email/passkey sign-in, account settings, handle change, sessions/devices list (incl. desktop OAuth grants — revoke), account deletion, data export |
| U7 | **Design system** | `components/ui.tsx` (~300 LOC) + Tailwind utilities. Needs tokens (light + dark), a component library (Radix/shadcn-class primitives), motion and spacing scale, and one brand shared with the desktop |
| U8 | **Accessibility + i18n** | ~32 `aria-` attributes in the app, no i18n framework, no keyboard/focus audit. Target WCAG 2.2 AA; set up i18n now (at least en + zh) |
| U9 | **Performance** | Google Fonts render-blocking, no code-splitting audit, no Lighthouse/Web Vitals budget in CI |

## 7. Backend / service (P1 → P2)

| # | Gap | Notes |
|---|---|---|
| B1 | **Single-node tunnel** | `TunnelManager` keeps `connections` / `pendingRequests` in process memory: one replica only, and a deploy drops every tunnel. Needs a shared routing layer (Redis pub/sub or NATS) so an event reaches the node holding the target tunnel, plus graceful drain. Fine to defer while traffic is small; R1's inbox should be designed to not assume one node |
| B2 | **Trust & safety** (smaller with visitor chat off) | Report peko / report seed, review queue, takedown (force-unexpose, yank seed), ban user/runtime, Turnstile on sign-up and publish |
| B3 | **Admin** | `/v1/admin/{gc,audit}` returns 403 in production (no admin role). Needs RBAC (admin/moderator) and an admin console: users, runtimes, pekos, seeds, reports, featured curation (`featured` exists with no UI) |
| B4 | **Notifications** | No transactional email. Needed for move/transfer approvals, device-code sign-in, new runtime registered, new API key, seed reports/takedowns |
| B5 | **Observability** | `metrics.ts` is a log-only shim. Needs OpenTelemetry, error tracking (Sentry), log shipping, dashboards and alerts (connected tunnels, relay latency, 5xx, auth failures), uptime checks |
| B6 | **Data + ops** | Postgres in docker on one Lightsail box: no managed DB, PITR backups, or restore drill. One environment: no staging, no preview deploys, IaC is shell scripts. A green deploy run is a no-op without `[lightsail]`. For dev stage, a **scale-to-zero staging** backend is enough to run runtime/desktop e2e |
| B7 | **Security hardening** | CORS `*` on Pages; the API needs an explicit CORS allow-list (`pekohub.ai`), CSP and security headers on both origins, secret rotation, dependency/container scanning in CI, a pen test before launch |
| B8 | **Dependency currency** | Fastify 4 (5 is current), Drizzle 0.31, Vite 5, React 18, Tailwind 3, vitest 1. Upgrade before launch, not after |
| B9 | **Legal / compliance** (smaller with visitor chat off) | Terms, Privacy Policy, cookie notice, content policy for published seeds, GDPR/CCPA export and deletion. Required before public sign-ups |

## 8. Suggested order

**Phase 1 — make the MVP clients work against the Hub (P0)**
1. Remove the web chat UI; anonymous visitor chat behind a default-off flag (§2).
2. C1 OAuth server + C2 device-code registration; desktop signs in and registers in one flow.
3. C3/C4 move every client to `api.pekohub.ai` and split web vs API URLs; C5 status route.
4. Desktop "add a remote peko" → contact + peer DM over the local runtime; retire `HubRemoteClient` (§2).
5. S1–S3 seed publish API, `peko seed` export, desktop create-from-seed.
6. C6 shared schema + cross-repo contract test; scale-to-zero staging backend.

**Phase 2 — public launch (P1)**
- R1 store-and-forward inbox, R2 ownership UI.
- U1–U5 website: IA and landing for the desktop funnel, honest states, profile and seed pages,
  OG previews, owner console.
- S4–S6 seed pages, review, naming. B2/B3 trust & safety + admin, B4 email, B5 observability,
  B6 managed DB + backups, B7 hardening, B9 legal.

**Phase 3 — scale and polish (P2)**
- B1 multi-node tunnel, U6 account depth, U7 design system, U8 a11y/i18n, U9 perf budgets,
  R3–R5, B8 upgrades.
